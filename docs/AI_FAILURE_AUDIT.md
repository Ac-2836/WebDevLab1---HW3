# AI Failure Audit

The lab requires three AI-induced defects, each with a description, diagnostic method, and verified refactored solution. Only defects that actually occurred are recorded. The three findings below were reproduced, traced and fixed; the notes distinguish a defect against the clarified expected behavior from a deviation from the original prompt.

## Defect 1: Countdown stopped after its module script was removed

- **Defect description:** While adding the Contact section for H3-04, the existing `<script type="module" src="main.js"></script>` was temporarily removed from `index.html`. Since `main.js` contains the countdown event listener and interval logic, the countdown output remained empty and did not update when a date was selected.
- **Diagnostic method:** During my review of the H3-04 change, I inspected the working-tree Git diff and compared it with the rendered page. The diff showed that `<script type="module" src="main.js"></script>` had been removed from `index.html`. The supplied screenshot showed the matching symptom: a date/time was selected and the Contact form was visible, but no countdown text appeared beside the date/time input. I checked `main.js` and confirmed that it registers the `change` listener for `#target-date` and contains the code that starts and renders the countdown. Since the module was no longer loaded, that listener could not run; this explained why selecting a date did not update the output. I therefore identified the removed module script as the cause, rather than a problem in the countdown functions or markup.
- **Commit that introduced the defect:** No commit. This was a temporary, uncommitted edit during H3-04. The verified `feat(html): landing form markup` commit retained the module script, so it would be inaccurate to attribute the defect to that commit.
- **Refactored solution:** I restored `<script type="module" src="main.js"></script>` immediately before `</body>` in `index.html`. I left the countdown markup and JavaScript unchanged.
- **Verification:** After restoring the script, I checked the rendered page with a future target and an expired target. The subsequent screenshots show a positive countdown and the terminal message `The event has started.`, confirming that the countdown behavior resumed.
- **Fix commit:** No separate fix commit; the script was restored before the H3-04 result was committed.

## Defect 2: Message accepted text shorter than the required minimum

- **Defect description:** The Contact form's Message `<textarea>` was marked `required` and capped at 500 characters, but it did not have a minimum length. As a result, a one-character message passed native browser validation and the submit flow proceeded, although the required minimum was 10 characters.
- **Diagnostic method:** I first reproduced the behavior on the Live Server page at `http://localhost:5501/` by entering valid Name and Email values and a one-character Message (`x`). In DevTools, I inspected `textarea#message` and its validity state: the element had no `minlength` attribute, `validity.tooShort` was `false`, and both the Message field and `#landing-form` passed `checkValidity()`. I then observed the form's simulated submit flow proceed from `Sending...` to `Thank you. Your message was sent.` This established that the short value was not being rejected before submission. To trace the source, I reviewed the `index.html` Git history and the form-markup diff: the H3-04 markup commit introduced the Message textarea with `required`, `maxlength="500"` and `rows="4"`, but no minimum. The initial WBS contract also omitted a minimum, so I did not claim the implementation violated that contract until the 10-character requirement was explicitly confirmed. After that requirement was confirmed, the missing native constraint was identified as the defect.
- **Commit that introduced the defect:** `feat(html): landing form markup` added the Message textarea without a minimum-length constraint.
- **Refactored solution:** I added `minlength="10"` to the existing Message textarea in `index.html`, retaining its `required`, `maxlength="500"` and `rows="4"` attributes. No JavaScript changes were needed because the submit handler already uses the form's native validity checks before submitting.
- **Verification:** On the Live Server page, I used real browser input with valid Name and Email values. With a 9-character Message, the browser reported `validity.tooShort === true`, and both the Message field and form were invalid. With a 10-character Message, `validity.tooShort === false`, and both field and form were valid. I also checked the change with `git diff --check`.
- **Fix commit:** `fix(html): add constraint minimum text length`.

## Defect 3: Countdown continued after the target date was cleared

- **Defect description:** After a countdown had started, clearing the `datetime-local` input left the old countdown visible and its interval kept updating it. This was confusing because the target field was empty while the page continued counting toward a date that was no longer selected.
- **Diagnostic method:** I reproduced the behavior on the Live Server page at `http://localhost:5501/`: I selected a future date and confirmed that the countdown began, then cleared the input and triggered its `change` event. The input became empty, but the countdown remained visible and decreased after waiting more than one interval tick. I then inspected the `change` handler in `main.js` and used the Git history to trace the empty-value branch to `feat(js): countdown rendering`. The branch returned immediately without calling `clearInterval(timerId)` or clearing the output, which explained both observed symptoms. For verification after the fix, I repeated the same steps: the output became empty immediately after clearing the target and stayed empty after waiting more than two seconds.
- **Commit that introduced the defect:** `feat(js): countdown rendering` added the empty-value branch that returned without stopping the active interval or clearing the output.
- **Refactored solution:** In the empty-value branch of `main.js`, I added `clearInterval(timerId)`, reset `timerId` to `null`, and set `countdownOutput.textContent` to an empty string before returning.
- **Verification:** On Live Server, I started a countdown to a future time, cleared the input, and confirmed that the output cleared immediately and remained empty after more than two seconds. `git diff --check` passed before the fix was committed.
- **Fix commit:** `fix(js): stop countdown when target is cleared`.
- **Requirement context:** The original H3-03 instruction said to return when the input value is empty, and the generated code followed that instruction. Stopping the timer and clearing the output was clarified as the desired behavior after the issue was reproduced. This context is recorded so the audit does not falsely claim that the original implementation violated an explicit instruction it had received.
